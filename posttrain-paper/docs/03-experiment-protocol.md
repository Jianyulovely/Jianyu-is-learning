# 实验协议（P1 等算力竞技场）

这份协议的作用：让审稿人挑不出方法学毛病。**方法学是这类论文唯一的护城河**——
你没有新算法，你只有「比别人做得更干净」这一条路。

---

## 1. 变量与控制

### 自变量
| 变量 | 水平 | 说明 |
|---|---|---|
| 方法 | SFT(gold) / RFT / DPO / Self-Consistency / Prompt-only | 5 个 |
| 预算 | 5 / 15 / 30 / 60 分钟 | 4 个点，用**总训练步数**卡 |
| 模型规模 | 0.5B / 1.5B / 3B | 3 个点 |
| 种子 | 42 / 1234 | 2 个 |

全因子 = 5 × 4 × 3 × 2 = 120 个格子。**但你不需要跑满**：

- Prompt-only 和 Self-Consistency **不训练**，没有预算轴上的 4 个点，只有 1 个点（它们在推理时花预算）；
- 所以实际训练 run 数 = (SFT + RFT + DPO) × 4 预算点 × 3 规模 × 2 种子 = 72 个 run。

72 个 run 在约 50 GPU 小时里跑完。**预算点必须按时间切，不能按 epoch 切**——按 epoch 切就等于让每个方法各跑到自己的收敛点，那比的就不是同一笔钱了。

### 必须固定的量（否则比较无意义）
- 基座模型版本（写死 revision hash，别用 `main`）
- 训练数据 prompt 集合（同一份，三个方法共用）
- tokenizer / chat template
- LoRA 配置（r=16, alpha=32, dropout=0.05, 全部 linear 层）
- 评测 prompt 模板与解码参数（greedy for eval）
- 评测集**绝不参与任何选择**（不调参、不 early stop、不挑 checkpoint）

### 允许不同的量（并在附录说明）
- 学习率：每个方法在自己的合理区间内，但**搜索预算相同**（比如各试 3 个值，取中位数预算点上的最优）
- batch size：受显存限制可不同，但必须换算成相同的「样本×epoch」总量

### 数据构造（`src/build_data.py`）
- **GSM8K**：从 train 抽 35%（≈2,615 条）。**剥掉原数据里的内联计算器标注**
  （`7-3=<<7-3=4>>4` → `7-3=4`；标注插在等号与结果之间，故删除而非替换），
  再统一成「推理文本 + 空行 + `The answer is \boxed{X}.`」。gold 取自 `####` 之后，**不参与**该清洗。
- **MATH**：从 `hendrycks_math` 的 algebra train 追加 400 条。该数据集只有 `problem / level / type / solution`，
  **没有 `answer` 字段**，gold 取 solution 末尾的 `\boxed{...}`，target 原样保留 solution。
- 两者合并后随机切 5% 作 dev（≈150 条），其余为 train（≈2,864 条）。
- 测试集（GSM8K test 1,319 / MATH-500 500）只含 `question + gold`，**不含 target**，避免解法泄漏进 prompt。

**为什么剥标注**：推理时没有任何工具会计算 `<<...>>`，保留它等于教模型输出一个永远无法被满足的动作；
且 MATH 一侧没有该标注，不剥会让两个数据源的「推理链长相」不一致，格式合规率也失去可比性。

## 2. 预算核算规范（本文核心，务必严格）

### 计时口径
```
GPU_hours = wall_clock_seconds * n_gpus / 3600
```

- 用 `torch.cuda.synchronize()` 包住计时区间，别把异步 kernel 启动算进去；
- 每个阶段单独记：采样 / 训练 / 评测；
- **计入预算**：采样 + 训练
- **不计入预算**：评测（对所有方法等同，且评测成本与方法无关）
- 数据准备不计入

### 为什么采样要计入
这是本文和「方法是 X 更好」类论文的关键区别：自洽投票的成本**全在采样**，
如果采样不计入预算，那自洽投票就是免费午餐，比较失去意义。**这一条必须在 intro 里讲清楚。**

### 报告方式
主图：**x = 累计 GPU·h，y = 准确率**，每个方法一条曲线，带 bootstrap 95% CI 阴影。
这张图就是全文的 figure 1。

## 3. 评测

### 解析器（三档，对应 P2 的复用）
| 档位 | 规则 | 用途 |
|---|---|---|
| lenient | 抓文本里最后一个数字 | 复现「宽松」结论 |
| standard | 优先 `\boxed{}`，否则最后一个数字 | 主指标 |
| strict | 要求答案在指定格式内且推理链非空 | 稳健性检查 |

**主指标用 standard，但三档都要报。** 只报一档会被问「你是不是挑了解析器」。

### 指标
- `accuracy`：主指标
- `format_compliance`：输出里能解析出答案的比例（这个指标本身是 P2 的核心，P1 里作为诊断）
- `answer_length`：输出 token 数（后训练常导致长度膨胀，必须报，否则会被质疑「你是靠啰嗦赢的」）

### 统计
- 每个配置 2 个种子，报**两个种子各自的数**，不要只报均值
- 主表给 mean ± std（n=2 时 std 意义有限，所以必须附 per-seed 表）
- 关键比较（自洽投票 vs SFT）做 **paired bootstrap**，10,000 次重采样，报 95% CI
- **不要做显著性检验的 p 值堆砌**，报效应量和 CI 更可信

## 4. 红线（碰了就是学术不端）

1. ❌ 在测试集上调超参 → 用 dev split（从 train 里切 5%）
2. ❌ 只报跑得好的 seed → 所有 run 都要进附录
3. ❌ 挑 checkpoint → 固定「最后一个 checkpoint」或「预算点对应的 checkpoint」
4. ❌ 编数字 → 表格里每个数都要能追溯到 `runs/` 下的 JSONL
5. ❌ 把别人的 baseline 数字直接抄进表里当自己的 → 要么复现，要么明确标注「引自 X」

第 5 条在小规模论文里特别常见，也特别容易被抓：别人是 7B 你 1.5B，直接对比毫无意义。

## 7. 如果你的时间只有一周

砍掉这些，按顺序：

1. 砍 0.5B（少 40% 算力，但保住一个规模）
2. 砍 DPO（最贵的方法；只留 SFT / RFT / 自洽投票）
3. 砍第二个 seed（**最后才砍**，砍了要接受审稿人质疑）
4. 预算点从 4 个减到 3 个（5 / 15 / 30 分钟）

砍完是 1 个规模 × 3 方法 × 3 预算点 × 1 seed ≈ 3 GPU·h，**半天就能跑完**，
但结论会很薄，只够一个技术博客或 workshop。这个 trade-off 你自己定。
